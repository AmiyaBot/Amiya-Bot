# core 运行时 · 插件加载器

`core/plugins/__init__.py` 的 `PluginsLoader` 是宿主唯一的插件装载器：扫描 `plugins/*.zip`、解析依赖并从远端补拉、按优先级倒序安装。它的几个行为特征（只扫顶层、异常吞掉、版本比对语义）是插件「装不上/装不对」问题的主要来源。

相关：[插件配置双轨](03-插件配置-基础.md) · [常见问题](09-常见问题.md) · [启动与单例](01-启动与单例.md)

---

## 1. 类型别名与构造（`core/plugins/__init__.py:13-20`）

```python
PLUGIN = Union[PluginInstance, AmiyaBotPluginInstance]   # :13
PLUGINS_MAP = Dict[str, PLUGIN]                          # :14

class PluginsLoader:                                     # :17
    def __init__(self, bot: MultipleAccounts):           # :18-20
        self.bot = bot
        self.plugins: PLUGINS_MAP = {}
```

- `PLUGIN` 是**两种插件基类的联合**：框架原生 `PluginInstance` 与本仓库扩展的 `AmiyaBotPluginInstance`（后者本身继承自前者）。写成 `Union` 是为了让 `isinstance` 检查有意义（`:59`、`:73`）。
- `PLUGINS_MAP` 是 `plugin_id -> 实例` 的映射，**插件身份由 `plugin_id` 唯一确定，不是目录名也不是文件名**。

## 2. `load_local_plugins()`（`:22-36`）

```python
async def load_local_plugins(self):
    for root, dirs, files in os.walk('plugins'):     # :23
        for file in files:                            # :24
            if file.endswith('.zip'):                 # :25
                res = await self.load_plugin_file(os.path.join(root, file))   # :26
                if res:
                    self.plugins[res.plugin_id] = res # :28
        break                                         # :29

    self.plugins = await self.check_requirements(self.plugins)   # :32

    log.info(f'loaded {len(self.plugins.keys())} plugin(s).')     # :34

    return await self.install_loaded_plugins()        # :36
```

**`:29` 的 `break` 是本节最需要理解的一行：**

- `os.walk('plugins')` 是**生成器**，默认递归遍历所有子目录。
- 但循环体末尾有 `break`（`:29`），**第一次迭代后就退出**——也就是**只处理 `plugins/` 根目录这一层**，子目录完全被忽略。
- 所以：`plugins/a.zip` ✅ 会被加载；`plugins/sub/a.zip` ❌ 被忽略；`plugins/sub/` 里的解压目录 ❌ 完全不看。
- **只处理 `.zip`**（`:25`）：解压出来的目录（`extract_plugin=True` 会解压，见 §3）不在扫描范围内。**把插件解压成目录手动放到 `plugins/` 下是无效的。**
- `root` 与 `dirs` 变量被接收但**从未使用**（`:23`）——进一步印证「只扫一层」是有意为之（如果要用 `root` 拼接路径就会递归了）。
- `break` 在 `for file in files` 内层循环**之后**，所以 `plugins/` 根目录下的**所有** zip 都会被处理，只是不进子目录。

**流程三步**：

1. 逐个加载 zip（`:23-29`），失败的不进 `self.plugins`。
2. `check_requirements` 做依赖解析与远端补拉（`:32`）。**它返回的是新字典**，直接覆盖 `self.plugins`——被判定不可安装的插件在这里被剔除。
3. `log.info` 打印最终数量（`:34`），然后 `install_loaded_plugins()`（`:36`）。

**返回值的坑**：`load_local_plugins()` 返回的是 `install_loaded_plugins()` 的返回值——**安装成功的插件数量（int）**，不是插件列表。`amiya.py:14` 忽略了返回值，但如果你写脚本想拿插件清单，应该读 `loader.plugins` 或 `bot.plugins`。

## 3. `load_plugin_file()`（`:38-42`）

```python
async def load_plugin_file(self, file: str) -> PLUGIN:
    async with log.catch(f'plugin load error({os.path.basename(file)}):'):   # :39
        res = self.bot.load_plugin(file, extract_plugin=True)                # :40
        if res:
            return res
```

- 核心就一行 `self.bot.load_plugin(file, extract_plugin=True)`（`:40`）——由 amiyabot 负责解析 zip 元信息并实例化插件。`extract_plugin=True` 表示把 zip 解压到磁盘（解压位置由 `extract_plugin_dest` 参数控制，本仓库未传 → 用默认位置）。
- `async with log.catch(...)`（`:39`）是**兜底**：任何异常被吞掉并记日志，函数返回 `None`。这意味着**插件加载失败不会中断启动流程**——一个坏插件只会静默消失。
- **实战排查**：插件没装上时，先看 `logs/running.log` 里有没有 `plugin load error(<文件名>):`。
- 失败时函数**隐式返回 `None`**（没有 `else` 分支）。调用方必须像 `:27` 那样判 `if res`。

> ⚠️ 因为异常被吞掉，插件构造期抛出的 `ValueError`（例如配置双轨的硬约束，见 [插件配置](03-插件配置-基础.md#3-构造期硬约束)）在启动日志里**只表现为一行 `plugin load error(...)`，看不到原因**。写插件时建议先在本地单独 import 一次，让异常真正抛出来。

## 4. `install_loaded_plugins()`（`:44-65`）

```python
async def install_loaded_plugins(self):
    count = 0
    for item in sorted(self.plugins.values(), key=lambda n: n.priority, reverse=True):   # :46
        if item.plugin_id in self.bot.plugins:      # :47-48
            continue

        try:
            res = self.bot.install_plugin(item)     # :51
            if res:
                count += 1
        except Exception as e:
            log.error(e, f'plugin install error({item.plugin_id}):')   # :55

    # 然后对所有插件执行懒加载（如果有的话）
    for plugin_id, item in self.bot.plugins.items():   # :58
        if isinstance(item, AmiyaBotPluginInstance):   # :59
            item.load()                                # :60

    if count:
        log.info(f'installed {count} plugin(s).')      # :63

    return count                                        # :65
```

三个关键设计：

1. **按 `priority` 倒序安装**（`:46`）。`priority` 是 `PluginInstance` 的属性，`AmiyaBotPluginInstance.__init__` 的默认值是 `1`（`core/plugins/customPluginInstance/amiyaBotPluginInstance.py:32`）。倒序 = **数字大的先装**。gamedata 插件用 `priority=999`（`pluginsDev/src/arknights/arknightsGameData/builder/__init__.py:48`）所以最先安装——这保证依赖它的插件安装时数据已就绪。
2. **跳过已安装的**（`:47-48`）。`self.plugins` 是「本次扫描到的」，`self.bot.plugins` 是「bot 上已有的」。这样 `install_loaded_plugins` **可以安全地重复调用**（控制台安装插件时会再走一次，见 `core/server/plugin.py:50-57`）。
3. **`install_plugin` 失败不中断**（`:50-55`）：单个插件报错只记日志，其余继续装。**「插件数量对不上」时不会有明显报错**，只能靠 `logs/running.log` 里的 `plugin install error(...)`。

**`:57-60` 的 `load()` 钩子**：

- 遍历的是 `self.bot.plugins`（**全部已装插件**，含本轮之前就装好的），不只是本轮新装的。
- 只对 `AmiyaBotPluginInstance` 调 `load()`（`:59-60`）。基类默认 `load()` 是空实现（`amiyaBotPluginInstance.py:250-251` 的 `def load(self): ...`），插件可以覆写它做「安装后但需要在所有插件就绪后才做的事」。
- **顺序意义**：`load()` 在所有插件的 `install_plugin` 之后统一调用，所以 `load()` 里可以安全地访问其它插件。
- 局部变量 `plugin_id`（`:58`）**未被使用**——无害。

## 5. `check_requirements()`（`:67-108`）

依赖解析的核心。

```python
async def check_requirements(self, plugins: PLUGINS_MAP, exists_plugins: Optional[PLUGINS_MAP] = None):
    final_res: PLUGINS_MAP = {}

    for pid, item in plugins.items():                      # :70
        allow_install = True                               # :71

        if isinstance(item, AmiyaBotPluginInstance) and item.requirements:   # :73
            for req in item.requirements:                  # :74
                if req.plugin_id == item.plugin_id:        # :75-76
                    continue                               # 自依赖，跳过

                exists = {**self.bot.plugins, **(exists_plugins or plugins), **final_res}   # :78

                # 本地已存在此依赖插件
                if req.plugin_id in exists:                # :81
                    if req.version and req.version != plugins[req.plugin_id].version:   # :83
                        allow_install = False              # :84
                        log.error(...)                     # :85-89
                    continue                               # :90

                # 本地不存在依赖，则从远端寻找依赖插件
                req_plugins = await self.find_plugin_from_remote(req)   # :93
                if req_plugins:
                    final_res = {**final_res, **req_plugins}            # :95
                else:
                    allow_install = False                                # :98
                    require = f'{req.plugin_id}@{req.version}' if req.version else req.plugin_id  # :99
                    log.error(...)                                       # :100-103

        if allow_install:
            final_res[pid] = item                       # :106

    return final_res                                    # :108
```

逐点说明：

- **只对 `AmiyaBotPluginInstance` 检查依赖**（`:73`）：原生 `PluginInstance` 没有 `requirements` 属性，因此不受管。
- **自依赖跳过**（`:75-76`）：`req.plugin_id == item.plugin_id` 时 `continue`，防止插件声明自己导致死循环。
- **`:78` 的 `exists` 合并顺序是重点**，优先级从低到高：
  1. `self.bot.plugins` —— bot 上**已安装**的
  2. `exists_plugins or plugins` —— 递归时传入的「已处理过的」映射，否则用当前待处理集合
  3. `final_res` —— 本轮**已判定可安装**的

  后面的覆盖前面的，所以 `final_res` 优先级最高。这个合并是为了让**同一批插件内部的互相依赖**能被识别（A 依赖 B，B 也在本批里）。
- **版本比对用的是字面量相等**（`:83`）：`req.version != plugins[req.plugin_id].version`。注意它读的是 **`plugins[req.plugin_id]`（传入字典）**，不是 `exists[req.plugin_id]`——**如果依赖插件是在 `self.bot.plugins` 里（已装）而不在本次 `plugins` 里，这行会 `KeyError`**。
  - 触发条件：插件 X 声明了 `Requirement('Y', version='1.0')`，而 Y 已经装在 bot 上、但本次 `load_local_plugins` 没扫到 Y 的 zip。
  - **实战含义**：出现插件加载异常时，先怀疑这条路径。
- **版本匹配是精确相等，不是语义化比较**（`:83`）：`'1.0'` 和 `'1.0.0'` 不相等。而 `compare_version_numbers`（[插件配置](04-插件配置-升级与审计.md#5-版本号比较)）才是做「大小比较」的那个——**两者语义不同，不要混淆**。
- **远端补拉**（`:93`）：本地缺失就调 `find_plugin_from_remote(req)`。
- **补拉结果并入 `final_res`**（`:95`）：`final_res` 同时充当「可安装集合」与「递归累积结果」，所以远端拉来的依赖也会被返回并最终安装。
- **失败只记日志**（`:98-103`）：插件被剔除出 `final_res`，但**不会抛异常**。日志文案是 `can not install plugin "X@v" because it requires "Y@v", but not found from remote.`

## 6. `find_plugin_from_remote()`（`:110-165`）

```python
async def find_plugin_from_remote(self, req: Requirement):
    req_plugins: PLUGINS_MAP = {}

    async def download_and_load(url):                             # :113
        filename = os.path.basename(url)                          # :114
        log.info(f'downloading plugin: {filename}')               # :116
        download_res = await download_async(url)                  # :118
        if download_res:
            with open(f'plugins/{filename}', mode='wb') as plugin_file:   # :120-121
                plugin_file.write(download_res)
            load_res = await self.load_plugin_file(f'plugins/{filename}')  # :123
            if load_res:
                req_plugins[req.plugin_id] = load_res             # :125
```

- **下载的 zip 会落盘到 `plugins/{filename}`**（`:120`）——即**远端补拉的插件会被持久化到本地**，下次启动 `load_local_plugins` 会直接扫到它。这是「自动补依赖」的机制。
- 文件名取自 URL 的 basename（`:114`）。

### 6.1 两条分支（`:128-159`）

```python
if req.official:                                   # :128
    # 官方插件从 cos 寻找依赖插件
    cos_url = f'{remote_config.remote.cos}/plugins/official/plugins.json'   # :130
    res = await http_requests.get(cos_url)         # :132
    if not res:
        return req_plugins                         # :134
    cos_plugins = {
        item['plugin_id']: remote_config.remote.cos
        + '/plugins/official/{plugin_id}-{version}.zip'.format(**item)      # :138
        for item in json.loads(res)                # :139
    }
    if req.plugin_id in cos_plugins:               # :142
        await download_and_load(cos_plugins[req.plugin_id])                 # :143
else:
    # 从插件服务寻找依赖插件
    req_url = f'{remote_config.remote.plugin}/getPluginRelease?plugin_id={req.plugin_id}'   # :147
    if req.version:
        req_url += f'&version={req.version}'       # :149
    res = await http_requests.get(req_url)         # :151
    if not res:
        return req_plugins                         # :153
    res_data = json.loads(res)                     # :155
    if res_data['code'] == 200:                    # :156
        await download_and_load(
            f'{remote_config.remote.cos}/plugins/custom/{req.plugin_id}/' + res_data['data']['file'],   # :158
        )
```

| 分支 | 触发条件 | 清单来源 | 下载地址 |
| --- | --- | --- | --- |
| **official** | `req.official == True`（`:128`） | `{cos}/plugins/official/plugins.json`（`:130`） | `{cos}/plugins/official/{plugin_id}-{version}.zip`（`:138`） |
| **custom** | `req.official == False`（默认） | `{plugin}/getPluginRelease?plugin_id=...`（`:147`，可带 `&version=`） | `{cos}/plugins/custom/{plugin_id}/{file}`（`:158`） |

**官方插件清单格式**（本仓库 `plugins/plugins.json` 就是同一份产物，19 个条目）：

```json
[{"description": "...", "document": "...", "logo": "data:image/png;base64,...",
  "name": "自定义回复", "plugin_id": "amiyabot-talking", "plugin_type": "official", "version": "1.7"}, ...]
```

由此可确认 `:138` 的 `.format(**item)` 只用到 `plugin_id` 与 `version` 两个字段（每个对象恰好含 `description/document/logo/name/plugin_id/plugin_type/version` 七个键，**没有 `file` 键**）。**官方插件的文件名是约定出来的** `{plugin_id}-{version}.zip`——与 `plugins/` 目录下实际文件名（`amiyabot-talking-1.7.zip`、`amiyabot-arknights-gamedata-4.1.zip` …）一致。

**custom 分支的返回结构**：`official=False` 时走 `{plugin}/getPluginRelease?plugin_id=...`（`:147-149`）取得响应，插件文件名从响应体 `res_data['data']['file']` 读取（`:155-158`）。**即非官方插件的文件名由远端返回，不由客户端约定**——这与上面 official 分支靠 `{plugin_id}-{version}.zip` 约定的方式不同，是两条分支的关键差异。

### 6.2 异常兜底与递归（`:161-165`）

```python
except Exception as e:
    log.error(e, desc='plugin download error:')
```

整段被 try/except 包住，异常只记日志。**`:134` 与 `:153` 的 `return req_plugins` 在 try 内部**，所以两种「拿不到依赖」的处理**不同**：

- `http_requests.get` 返回假值（`:133`、`:152`）→ 提前 `return req_plugins`（**跳过递归依赖检查**）
- 抛异常（`:161`）→ 记日志后继续走到 `:165` 的递归

```python
# 检查依赖的依赖
return await self.check_requirements(req_plugins, {**self.plugins, **req_plugins})   # :164-165
```

- 对刚下载的依赖插件**再跑一遍依赖检查**——这就是「递归依赖」的实现。
- 第二个参数 `exists_plugins` 传的是 `{**self.plugins, **req_plugins}`：即「本次已加载的 + 刚拉下来的」，作为递归层的「已存在」集合（对应 `:78` 的合并）。
- **递归没有深度限制**：`check_requirements` → `find_plugin_from_remote` → `check_requirements` 的循环中**没有 seen 集合**。不过 `:75-76` 的自依赖检查和「下载后落盘、再 `load_plugin_file` 时已能被识别」通常能打破循环。

## 7. 加载过程的完整时序

```
amiya.py:13   PluginsLoader(bot).load_local_plugins()
                 │
                 ├─ os.walk('plugins') + break        core/plugins/__init__.py:23-29
                 │    └─ load_plugin_file(zip)   ────► :38-42  (log.catch 吞异常)
                 │         └─ bot.load_plugin(file, extract_plugin=True)
                 │
                 ├─ check_requirements(plugins)       :67-108
                 │    ├─ 自依赖跳过                      :75-76
                 │    ├─ 已在 bot.plugins / 本批 / final_res 中 → 检查版本 :81-90
                 │    └─ 缺失 → find_plugin_from_remote  :93
                 │         ├─ official → {cos}/plugins/official/plugins.json   :128-143
                 │         ├─ custom   → {plugin}/getPluginRelease             :147-158
                 │         ├─ 下载落盘 plugins/{filename}                       :120-123
                 │         └─ 递归 check_requirements                          :164-165
                 │
                 ├─ install_loaded_plugins()          :44-65
                 │    ├─ 按 priority 倒序，跳过已装                 :46-48
                 │    ├─ bot.install_plugin(item)（单个失败只记日志） :50-55
                 │    └─ 对所有 AmiyaBotPluginInstance 调 load()    :58-60
                 │
                 └─ 返回安装成功的数量 (int)                       :65
```

**控制台安装/升级插件走的是同一条链**，但由 `core/server/plugin.py:50-57` 的 `use_loader` 手工串起三步（新建 `PluginsLoader` 实例 → 跳过目录扫描 → 直接 `load_plugin_file` → `check_requirements` → `install_loaded_plugins`）。见 [控制台 API · 插件管理](08-控制台API-业务接口.md)。

## 8. 已知约束与坑

| # | 约束 | 位置 | 表现 |
| --- | --- | --- | --- |
| 1 | `plugins/` **只扫顶层**，`os.walk` 后立刻 `break` | `core/plugins/__init__.py:23-29` | 子目录里的 zip 永远不加载 |
| 2 | **只认 `.zip`**，解压目录无效 | `core/plugins/__init__.py:25` | 手动放解压目录不起作用 |
| 3 | `load_plugin_file` 用 `log.catch` 吞掉所有异常 | `core/plugins/__init__.py:39` | 插件加载失败只留一行日志，`ValueError` 原因看不到 |
| 4 | `:83` 用 `plugins[...]` 而非 `exists[...]` | `core/plugins/__init__.py:83` | 依赖已装在 bot 上但不在本批扫描结果中时 `KeyError` |
| 5 | 版本比对语义与 `compare_version_numbers` 不一致 | `:83`（字面量相等）vs `amiyaBotPluginInstance.py:470-491`（数字比较） | `'1.0'` vs `'1.0.0'` 两处结论相反 |
| 6 | 递归补依赖无 seen 集合 | `:93` ↔ `:165` | 互相依赖且都缺失时理论上可无限递归 |
| 7 | 安装失败会留下半成品 zip | `core/server/plugin.py:150-157` + `:157` 不删文件 | 下次启动重复尝试加载并再次报错 |
| 8 | 重复安装返回「失败」但其实已装 | `core/server/plugin.py:154-157` + `:47-48` 跳过已装 | 误导性的错误提示（`count=0` → 500） |
| 9 | 依赖插件被落盘到 `plugins/` | `:120-121` | 远端补拉的插件会持久化，下次启动直接扫到 |
| 10 | 只有 `AmiyaBotPluginInstance` 受依赖检查 | `:73` | 原生 `PluginInstance` 声明 `requirements` 无效 |
