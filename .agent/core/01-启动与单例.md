# core 运行时 · 启动链路与全局单例

`amiya.py` 的启动顺序本身就是一份隐式的初始化协议。`core/__init__.py` 的绝大多数语句是模块级的，**任何 `import core` 都会执行它们**：建目录、读配置、建库建表、构造 `bot` 单例、挂载钩子、发起一次网络请求。排查启动问题从这里开始。

---

## 1. `amiya.py`：程序入口

`amiya.py` 只有 35 行，行序即初始化协议。

`amiya.py:1-8` 的 import 顺序即协议：`import core.frozen` **必须最先**，随后 `from core.plugins import PluginsLoader`，再 `from core import app, bot, init_task, BotResource`（**import 即构建全部单例**）。

`amiya.py:11-18` 的 `run_amiya`：

| 顺序 | 语句 | 行号 | 说明 |
| --- | --- | --- | --- |
| 1 | `BotResource.download_bot_resource()` | `amiya.py:21` | **同步阻塞**下载并解压资源包 |
| 2 | `sys.path += [...]` | `amiya.py:23-27` | 追加 3 个路径 |
| 3 | `asyncio.run(main())` | `amiya.py:29` | 进入事件循环 |
| 4 | `PluginsLoader(bot).load_local_plugins()` | `amiya.py:13-14` | 装载 `plugins/*.zip` |
| 5 | `asyncio.create_task(task) for task in [*init_task, *tasks]` | `amiya.py:17` | 协程转 Task |
| 6 | `await asyncio.wait(all_tasks)` | `amiya.py:18` | 并发等到**全部**任务结束 |

要点：

- **第 1 步发生在事件循环之外。** `download_bot_resource()` 是普通同步函数（`amiya.py:21` 未 `await`），在 `asyncio.run` 之前执行，启动时会先卡住一段时间做网络 IO 与解压。失败时抛出的异常**捕获不到**——`amiya.py:30-31` 的 `except KeyboardInterrupt` 只处理 Ctrl-C，所以资源下载失败会直接向上抛出并终止进程。
- **第 2 步是冻结打包版的运行期补丁**（`amiya.py:23-27`）：`sys.path` 追加 `os.path.dirname(sys.executable)`（`:24`）、`os.path.abspath('resource/env/python-dlls')`（`:25`）、`os.path.abspath('resource/env/python-standard-lib.zip')`（`:26`）三项，给 PyInstaller 单文件版准备：exe 所在目录、运行期从资源包解压出的 Python DLL 目录与标准库 zip。路径用**相对当前工作目录**的 `os.path.abspath('resource/...')`，所以 **CWD 必须是仓库根**，否则这三条路径全部指向错位置。
- **第 5 步的 `tasks` 由调用方注入。** `run_amiya(tasks: List[Coroutine] = [])`（`amiya.py:11`）默认空列表，此时只等 `init_task`。而 `init_task` 里已有 `heartbeat()` 与 `run_main_timed_tasks()`（见 §3.5），所以**即使不传 tasks，进程也不会退出**——它会挂着等定时任务。想跑「只加载插件不启动 bot」的脚本，不能靠不传 tasks 来结束。
- **`__main__` 入口**（`amiya.py:34-35`）：`run_amiya([bot.start(launch_browser=True), app.serve()])`。`bot.start()` 拉起机器人（含 Playwright 浏览器），`app.serve()` 拉起控制台 HTTP 服务，两者并发等待。
- **`except KeyboardInterrupt: pass`**（`amiya.py:30-31`）让 Ctrl-C 干净退出，不打印堆栈。

## 2. `core/frozen.py`：冻结模式路径修正与保活 import

`core/frozen.py` 全文 25 行，做两件事。

### 2.1 冻结模式下的资源路径修正（`core/frozen.py:20-25`）

这段代码把 `FontStyle.file`、`ChainConfig.md_template`、`ChainConfig.md_template_dark` 三个静态资源指向 `DIR_PATH/_assets/...`，其中 `DIR_PATH = os.path.dirname(os.path.realpath(sys.executable))`。

- `hasattr(sys, 'frozen')` 是 PyInstaller 运行时给 `sys` 打的标记。
- 冻结版中 `sys.executable` 就是 exe 自身，所以 `DIR_PATH` = exe 所在目录；三个静态资源（字体、两套 Markdown 模板）从该目录下的 `_assets/` 取。
- 这三个路径与打包脚本里 `shutil.copytree(f'{venv}/amiyabot/_assets', f'{dist}/_assets')` 的产物一一对应（`build/package.py:167-169`）——`_assets` 是从 `amiyabot` 包内拷出来的。
- `FontStyle` / `ChainConfig` 的导入在 `core/frozen.py:17-18`。

### 2.2 一串保活 import（`core/frozen.py:3-15`）

这一串是 `srsly`（`:3`）、`dhash`（`:4`）、`requests_html`（`:5`）、`core.customPluginInstance`（`:7`）、`from . import server`（`:9`）、`jieba.posseg`（`:10`）、`core.lib.baiduCloud`（`:11`），以及 `core.database` 的 `bot`/`group`/`messages`/`user`（`:12-15`）。

**这串 import 的目的不是「使用」，而是让 PyInstaller 的静态分析能发现这些模块，从而把它们一并收进打包产物。** PyInstaller 靠扫描 import 语句构建依赖图，而本项目大量模块是**动态导入**的——运行期才通过字符串或插件 zip 加载，静态分析看不到：

- `srsly`（`:3`）全仓库**只此一处**引用，纯粹是收集锚点。
- `core.database` 的 `group`（`:13`）与 `core/server`（`:9`）同样**只在这里出现**：库模块 `group.py` 只被插件引用，而插件是运行期才加载的 zip；`core/server/*` 则完全没有直接引用，仅靠 `from . import server` 让 `core/server/__init__.py` 被静态发现，进而发现 8 个控制器模块。
- 其余几个（`dhash`、`requests_html`、`jieba.posseg`、`baiduCloud`）在别处也有使用，但都在**运行期才触达的代码路径**中，静态分析不一定能覆盖，这里再显式 import 一次作为兜底。

`amiya.py:4` 把 `import core.frozen` 放在所有 import 之前，就是为了触发这份清单。

> ⚠️ **不要随手删 `core/frozen.py` 里的任何 import。** 删掉在源码运行下毫无影响（这些模块本来也会被别处导入），但在 PyInstaller 单文件版里会表现为 `ModuleNotFoundError`——而且只在打包产物上复现，源码调试完全看不出来。

### 2.3 `core/frozen.py:7` 指向的是转发模块，不是包

`core.customPluginInstance` 解析到的是**文件** `core/customPluginInstance.py`，其全文只有 1 行：

```python
from core.plugins.customPluginInstance import *   # core/customPluginInstance.py:1
```

而真正的实现包是目录 `core/plugins/customPluginInstance/`。两者不冲突：

- `core` 是包（有 `core/__init__.py`），其下的 `customPluginInstance` 属性由同名**模块文件**满足；
- `core.plugins.customPluginInstance` 是完全独立的另一条路径（`core` → `plugins` → `customPluginInstance` 包）；
- 两者是**父子不同层级上的同名物**，不构成遮蔽冲突。

**转发模块存在的意义**：兼容**旧版插件代码的 import 路径**。V5 时期自定义插件实例很可能就放在 `core/customPluginInstance.py`，插件里写的 `from core.customPluginInstance import AmiyaBotPluginInstance` 在 V6 重构后仍要能跑通——`plugins/*.zip` 里的插件是历史产物，不可能跟着宿主一起改。

`core/customPluginInstance.py` 用的是 `import *`，而包的 `__init__.py` 没有定义 `__all__`，因此 `import *` 导出三个公开名字 `AmiyaBotPluginInstance` / `LazyLoadPluginInstance` / `Requirement`。

> **新代码用 `from core.plugins.customPluginInstance import ...`**（与 `core/__init__.py:23` 一致）；`core/customPluginInstance.py` 只作老路径兼容保留，不要往里加新东西。

## 3. `core/__init__.py`：全局单例在 import 时构建

`core/__init__.py` 共 138 行，是本项目最核心的文件。它绝大部分语句是**模块级**的——**任何 `import core` 都会执行它们**。这不是偷懒，而是刻意设计：让宿主配置在「第一次 import」时一次性完成校验和初始化，后续任何模块拿到的都是同一份单例。

### 3.1 导入区（`core/__init__.py:1-23`）

导入分三段：标准库与 `amiyabot`/`amiyahttp`（`:1-13`），宿主内部模块（`:15-21`），以及插件实例基类（`:23`）。

三点值得注意：

1. **`from amiyabot import *`（`:9`）是全局的**。它把 `bot`、`log`、`Message`、`Chain`、`Union`、`MultipleAccounts` 等名字全部引入 `core` 命名空间。因此插件里普遍写 `from core import log, Message, Chain` 也能工作——它其实是从 `core` 命名空间转发出来的 amiyabot 名字（例如 `pluginsDev/src/arknights/gacha/main.py:10`）。
   > 副作用：`core/__init__.py:39` 定义的 `bot = MultipleAccounts(...)` 会**覆盖** `import *` 带进来的同名符号。本仓库所有 `from core import bot` 拿到的都是这里定义的 `MultipleAccounts` 实例。
2. **`amiyahttp` 是第二个框架依赖**，用于控制台 HTTP 服务（`HttpServer` / `ServerConfig` / `AuthKey`）。它**不在 `requirements.txt` 里**，是被 `amiyabot` 间接带入的。
3. `AmiyaBotPluginInstance` 与 `Requirement` 从 `core.plugins.customPluginInstance` 包导入（`:23`），随后插件里 `from core import AmiyaBotPluginInstance` 即可。这是插件写法的官方姿势。

### 3.2 建目录与读配置（`core/__init__.py:25-38`）

依次执行 `create_dir('plugins')`（`:25`）、读 `config/server.yaml`（`:27`）与 `config/prefix.yaml`（`:28`）、构造 `ServerConfig`（`:29`）并清空 `api_prefix`（`:30`）、构造 `HttpServer`（`:31`）、声明三个免鉴权路径 `allow_path`（`:32-36`）、构造 `AuthKey`（`:37`）、`app.use_plugin(auth)`（`:38`）。

| 语句 | 行号 | 关键点 |
| --- | --- | --- |
| `create_dir('plugins')` | `:25` | **相对 CWD** 创建插件目录；实现见 `core/util/common.py:149-156`（`os.makedirs`） |
| `read_yaml('config/server.yaml')` | `:27` | 返回 `attridict`，所以能用 `serve_conf.host` 属性访问（`core/util/yamlManager.py:15-28`） |
| `app_conf = ServerConfig()` | `:29` | 默认配置对象 |
| `app_conf.api_prefix = ''` | `:30` | 清空前缀，使路由路径就是方法名/显式路径（见 [控制台 API](07-控制台API-机制与基础接口.md)） |
| `HttpServer(...)` | `:31` | 传入 `host` / `port` / `config` 三个位置参数 |
| `allow_path` | `:32-36` | **三个免鉴权路径**，含义见 [控制台 API · allow_path 白名单](07-控制台API-机制与基础接口.md#7-allow_path-白名单三个路径分别服务谁) |
| `auth = AuthKey(serve_conf.authKey, 'authKey', allow_path)` | `:37` | 第二个参数 `'authKey'` 是**鉴权参数的字段名**；第三个参数是免鉴权白名单 |
| `app.use_plugin(auth)` | `:38` | 挂载鉴权中间件 |
| `app.add_static_folder('/plugins', 'plugins')` | `:41` | 把本地 `plugins/` 目录挂到 URL `/plugins` 下 |

> **`config/server.yaml` 的三个字段是强制的**：`config/server.yaml:1-3` 为 `host: 127.0.0.1` / `port: 8088` / `authKey:`（空值）。结合 `allow_path` 的设计（`core/__init__.py:32-36`）可以确定：**白名单路径在鉴权插件中始终放行**，这是远端控制台能直接拉数据的原因。
>
> Docker 部署下 `entrypoint.py:57` 会把 `host` 强制改成 `0.0.0.0`，并用 `AUTH` 环境变量写 `authKey`（`entrypoint.py:58-59`）——这是容器里能被外部访问的前提。

### 3.3 `bot` 单例：模块级构建（`core/__init__.py:39`）

即 `bot = MultipleAccounts(*BotAccounts.get_all_account())`（`:39`）。

这是全文最关键的一行，也是「为什么 import core 会碰数据库」的答案：

- `BotAccounts.get_all_account()`（`core/database/bot.py:55-67`）会**查询 `amiya_bot` 数据库**，遍历所有账号，跳过 `is_start` 为 0 的（`core/database/bot.py:61-62`），对每个存活账号调 `build_conf` 并**构造一个 `AmiyaBot` 实例**（`core/database/bot.py:64-65`）。
- `core/database/bot.py:18` 的 `db = connect_database('amiya_bot' if is_mysql else 'database/amiya_bot.db', is_mysql, config)` 在同一模块顶层执行——**连接数据库 + 建表**。
- 因此执行链是：`import core` → `core/__init__.py:16` 导入 `BotAccounts` → `core/database/bot.py:18` 建库建表 → `core/__init__.py:39` 读取并构造 bot 实例。

**实战含义**：

- 数据库文件不存在时会**现场创建**，不会报错；但 `MultipleAccounts` 是空的，`bot.start()` 什么都不会启动。排查「bot 不上线」的第一步就是查 `BotAccounts` 表里有没有 `is_start=1` 的记录。
- 由于建表在 `core/__init__.py:39` 之前完成，`BotAccounts.get_all_account()` 不会因「表不存在」失败。
- **同一个进程里 `bot` 只有一份**，所有 `from core import bot` 拿到的都是它。控制台端点 `core/server/bot.py:100` 的 `bot.append(...)`、`core/server/bot.py:109` 的 `del bot[data.appid]` 都是直接改这个单例——**运行期增删账号无需重启**。

`MultipleAccounts` 支持的容器协议（`in`、`[]`、`append`、`del`）在仓库中被广泛使用：`if item['appid'] in bot`（`core/server/bot.py:54`）、`bot[item.appid]`（`core/__init__.py:65`）、`bot.append(...)`（`core/server/bot.py:100`）、`del bot[data.appid]`（`core/server/bot.py:109`）、`for item in bot`（`core/__init__.py:72`）。

### 3.4 消息记录缓冲与工具函数（`core/__init__.py:43-68`）

这一区定义的名字：`message_record = []`（`:43`）、`set_prefix()`（`:46-50`）、`exec_before_init(coro)`（`:53-55`）、`add_allow_path(path)`（`:57-59`）、`send_to_console_channel(chain)`（`:62-68`）。

| 名字 | 行号 | 作用与坑 |
| --- | --- | --- |
| `message_record` | `:43` | **模块级可变列表**作为消息缓冲。模块级 `global` 语义要求：`:114` 声明 `global message_record`，`:116` 重新赋值 `message_record = []`（换列表对象而非清空原列表）——这是必须的，因为定时任务读的是模块属性 |
| `set_prefix()` | `:46-50` | 从 `config/prefix.yaml` 读 `prefix_keywords` 与 `jieba_del_words`；前者调 `bot.set_prefix_keywords`，后者调 `jieba.del_word` 把这些词从 jieba 词典里删掉，避免「兔子」被切成一个词而影响分词匹配 |
| `exec_before_init(coro)` | `:53-55` | **插件注册启动协程的官方入口**。它接收的是**已经调用过的协程对象**（`coro()` 在 `:54`），所以调用方写 `exec_before_init(some_async_func())`（带括号）。它把协程塞进 `init_task`，最终在 `amiya.py:17` 被 `asyncio.create_task` 消费 |
| `add_allow_path(path)` | `:57-59` | 运行期给 `auth` 加免鉴权路径。**插件可以调用它来暴露自己的接口**——这是插件对外提供 HTTP 接口的唯一正规途径 |
| `send_to_console_channel(chain)` | `:62-68` | 遍历 `is_main == 1` 的账号（`:63`），取 `bot[item.appid]`（`:65`），若配置了 `console_channel` 就发消息（`:67-68`）。**注意 `instance` 可能为 `None`**（账号未启动），`:67` 的 `and instance` 就是这个保护 |

> ⚠️ **`init_task` 的定义位置在文件末尾**（`core/__init__.py:137`），但 `exec_before_init`（`:53-55`）在它**之前**就引用了它。这在 Python 里可行只是因为 `exec_before_init` 的函数体直到被调用时才求值 `init_task`——**只要调用发生在模块加载完成之后**。若在 `core/__init__.py` 执行过程中（例如某个被 `:15-23` 导入的模块在 import 期）调用 `exec_before_init`，会 `NameError`。这是真实存在的时序约束。

### 3.5 心跳与定时任务启动（`core/__init__.py:71-80`）

`heartbeat()`（`:71-76`）对**每个已加载的 bot 实例**上报 `appid` 到 `{plugin}/heartbeat`——这是**纯客户端行为**：`http_requests.get(f'{remote_config.remote.plugin}/heartbeat?appid={item.appid}', ignore_error=True)`。服务端收到后如何处理不属于本公开仓库的说明范围。`remote_config.remote.plugin` 默认值 `https://cdn.amiyabot.com`（`core/config/remote.py:9`）实际指向插件商店后端。
- `ignore_error=True`（`:75`）保证网络抖动不会打断心跳循环。
- `run_main_timed_tasks()`（`:79-80`）把**定时任务的执行权交给框架**：`bot.run_timed_tasks()` 会阻塞并周期性触发所有 `@bot.timed_task` 注册的回调。**没有它，§4 的三个定时任务永远不会执行**——这也解释了为什么它必须出现在 `init_task` 里（`:137`）。

## 4. 四个模块级钩子：消息记录、异常上报、定时任务

`core/__init__.py:83-134` 用 4 个装饰器在导入期把钩子挂到 `bot` 上。

### 4.1 `@bot.message_before_handle`（`core/__init__.py:83-94`）

装饰器是 `@bot.message_before_handle`（`:83`，**不带括号**），函数体只做一次 `message_record.append({...})`（`:85-94`），写入 `app_id` / `user_id` / `channel_id` / `msg_type` / `classify` / `create_time` 六个键。

- 函数签名 3 个参数：`data: Message`、`factory_name: str`、`_`（第三个被忽略，很可能是消息链/上下文）。
- 只做一件事：**把消息元数据追加进内存缓冲**，不落库。字段与 `MessageRecord` 表（`core/database/messages.py:13-19`）一一对应。
- `data.message_type or 'channel'`（`:90`）做了兜底：`message_type` 为空时记为 `'channel'`。
- `classify` 恒为 `'call'`（`:91`），是消息分类标记。
- **设计意图**：「before handle」意味着**在所有插件处理之前**记录，因此即使消息后来被前缀/权限拦下，也会计入统计。这解释了 dashboard 的调用量为什么等于「收到的消息数」而不是「被响应的消息数」。
- **性能坑**：这是**每条消息都会执行**的热路径，只往列表里 append 一个 dict，开销极小——这是刻意的设计。**不要在这个钩子里加耗时逻辑**。

### 4.2 `@bot.on_exception()`（`core/__init__.py:97-109`）

签名是 `(err: Exception, instance: BotAdapterProtocol, data: Union[Message, Event])`（`:98`）；函数体拼出 Adapter / Bot / Channel / User 与正文（`:99-105`），用 `Chain().text(...).text_image(traceback.format_exc())`（`:106`）渲染堆栈图片，最后 `await send_to_console_channel(content)`（`:109`）。

- **注册时带括号** `@bot.on_exception()`（`:97`）——它是工厂式装饰器，与 `@bot.message_before_handle`（`:83`，不带括号）不同。写插件时这点极易混淆。
- 参数 `err` 实际**没被使用**，异常内容通过 `traceback.format_exc()`（`:107`）获取——它依赖**当前异常上下文**（`sys.exc_info()`），而不是 `err` 对象。
- `data.text if isinstance(data, Message) else data.event_name`（`:104`）：消息事件取 `text`，其它事件取 `event_name`。
- `.text_image(traceback.format_exc())`（`:107`）：把堆栈渲染成图片。QQ 平台对超长文本不友好，图片更易读。
- 最终走 `send_to_console_channel`（`:109`）→ 发到主账号的 `console_channel`。**如果没配 `console_channel`，异常会静默丢失**（`:67` 的条件不满足），这是排查线上问题时的常见盲点：先确认 `BotAccounts.console_channel` 有值。

### 4.3 三个 `@bot.timed_task`

| 装饰器 | 行号 | 行为 |
| --- | --- | --- |
| `@bot.timed_task(each=60)` | `:112-116` | **60 秒批量落库** |
| `@bot.timed_task(each=60, run_when_added=True)` | `:119-121` | **60 秒心跳** |
| `@bot.timed_task(each=3600, run_when_added=True)` | `:124-134` | **每小时清理 90 天前记录** |

**(1) 60 秒批量落库（`:112-116`）**

它 `global message_record`（`:114`）后 `batch_insert(copy.deepcopy(message_record))`（`:115`），再 `message_record = []`（`:116`）换一个新列表。

- `global message_record`（`:114`）是必须的：不声明的话 `:116` 的赋值会创建**局部**变量，缓冲永远清不掉。
- `copy.deepcopy(...)`（`:115`）先深拷贝再交给 `batch_insert`——避免批量插入过程中消息钩子继续 append 到同一列表。
- **注意它没有 `run_when_added=True`**，与另外两个形成对比：首次落库要等 **60 秒**。所以刚启动后立刻查 `MessageRecord` 会是空的，这是正常现象。
- `batch_insert` 来自 `amiyabot.database`（通过 `core/database/messages.py:1` 的 `from amiyabot.database import *` 进入命名空间）。
- **坑：进程被强杀（Ctrl-C / SIGKILL / 容器 stop）时，缓冲里最多 60 秒的消息会丢失。** 这是刻意的取舍——避免每条消息一次磁盘写。

**(2) 60 秒心跳（`:119-121`）**

函数体只有 `await heartbeat()`。

- `run_when_added=True` 表示**注册后立刻跑一次**，不等第一个 60 秒周期。
- 心跳在 `init_task` 里还有一份裸的 `heartbeat()`（`:137`）——所以进程启动时 `heartbeat` 实际上会被调用**两次**。这是无害的重复上报（同一 appid 的重复心跳），可用于解释上线状态的上报时延。

**(3) 每小时清理 90 天前记录（`:124-134`）**

它把 `(datetime.datetime.now() + datetime.timedelta(days=-90)).strftime('%Y%m%d')` 再经 `time.strptime` / `time.mktime` 转回时间戳，最后 `MessageRecord.delete().where(MessageRecord.create_time < timestamp).execute()`。

- 算法：**当前时间 - 90 天 → 格式化 '%Y%m%d' → 丢弃时分秒 → 转回时间戳**。阈值被**截断到当天零点**。
- 后果：实际保留期略长于 90 天（最多多留不到 24 小时），且删除是**按天粒度**的。这是有意的简化——避免每次计算都带时分秒导致边界抖动。
- 用 `time.mktime` + `time.strptime`（**本地时区**），不是 `utcfromtimestamp`。所以容器时区设置会影响清理边界。
- `each=3600` + `run_when_added=True`：启动时立刻清一次。**大数据量下，启动的第一次清理可能阻塞事件循环**（peewee 是同步 ORM，这个 delete 在异步函数里直接执行，没有 `run_in_thread_pool` 包装）。

### 4.4 模块末尾（`core/__init__.py:137-138`）

`init_task = [heartbeat(), run_main_timed_tasks()]`（`:137`），`set_prefix()`（`:138`）。

- `init_task` 里存的是**协程对象**（`heartbeat()` 带括号立即创建协程），在 `amiya.py:17` 被 `asyncio.create_task` 转成 Task。
- `set_prefix()`（`:138`）在**模块加载的最后**执行——它依赖 `bot`（`:39`）已经存在。如果把它挪到 `:39` 之前会 `NameError`。

**`import core` 的顺序检查表**（排查 `import core` 报错时按此顺序看）：

1. `create_dir('plugins')` → `:25`
2. 读 `config/server.yaml`、`config/prefix.yaml` → `:27-28`
3. `HttpServer` 构造 → `:31`
4. `AuthKey` + `use_plugin` → `:37-38`
5. 导入 `core.database.*`（触发建库建表）→ `:15-16`
6. `MultipleAccounts` 构造（读账号）→ `:39`
7. 挂载 4 类钩子 → `:83-134`
8. `init_task` 赋值 → `:137`
9. `set_prefix()` → `:138`

> **`core/config/remote.py` 的副作用也在这条链上**：`core/__init__.py:17` 导入 `remote_config` 时，`core/config/remote.py:35` 的 `remote_config = init('config/remote.yaml')` 会执行；而 `Remote.__init__`（`core/config/remote.py:12-23`）会**同步请求 `{plugin}/api/v1/remote` 覆盖默认值**。也就是说 **`import core` 会发起一次网络请求**（失败则静默回退，`:22-23` 的裸 `except`）。这会给启动增加一次网络往返，离线环境下会等到超时。详见 [工具 · 配置](../tools/01-配置.md)。
