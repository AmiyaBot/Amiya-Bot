# core 运行时 · 插件配置：升级、审计与清理

插件升级时，宿主按版本号比对并**自动补齐新配置字段**，同时写入审计记录；升级满 N 天后清理废弃配置项。本文覆盖这条时间线，以及 `Requirement`、`compare_version_numbers`、`remove_uncommon_elements` 等辅助设施。

配置的读写与降级链见 [插件配置 · 基础](03-插件配置-基础.md)。

相关：[插件加载器](02-插件加载器.md) · [数据库 · 其余表](06-数据库-其余表.md) · [常见问题](09-常见问题.md)

## 1. 审计表 `PluginConfigurationAudit`

`amiya_plugin` 库的第二张表（`core/database/plugin.py:25-32`）：

```python
@table
class PluginConfigurationAudit(PluginBaseModel):
    id: int = AutoField()                       # :27
    plugin_id: str = CharField()                # :28
    channel_id: str = CharField(null=True)      # :29
    audit_time: datetime = DateTimeField()      # :30
    audit_reason: str = CharField()             # :31
    version: str = CharField()                  # :32
```

| 字段 | 行号 | 说明 |
| --- | --- | --- |
| `id` | `:27` | **显式 `AutoField()` 自增主键** |
| `plugin_id` | `:28` | 插件 ID |
| `channel_id` | `:29` | 频道 ID（`null=True`），全局为 `''` |
| `audit_time` | `:30` | **`DateTimeField`**（不是时间戳），用 `datetime.now()` 写入 |
| `audit_reason` | `:31` | 审计原因 |
| `version` | `:32` | 插件版本 |

**`audit_reason` 的三个取值**：

| 值 | 写入行 | 触发时机 |
| --- | --- | --- |
| `'Plugin Initialize'` | `amiyaBotPluginInstance.py:80` | 插件首次安装，写入 global_default |
| `'Plugin Upgrade'` | `:95`、`:116` | 版本落后，`merge_dict` 补全配置后 |
| `'Plugin Configuration Deprecated'` | `:201`、`:216` | 清理废弃配置项后 |

- **`version` 是 CharField 而非数值**（`:32`），与插件 `version` 参数一致。
- **`channel_id` 可空**（`:29`），但实际写入时全局用 `''`（`:78`、`:189` 等），所以 NULL 几乎不会出现。
- **这张表的 id 是自增的**，`deprecated_config_delete` 用 `fn.MAX(id)` 而非 `MAX(audit_time)` 取最新（`amiyaBotPluginInstance.py:136-149`）。
- **它只增不减**：没有清理机制。但每个插件/频道最多每次升级一条，量级可控。

## 2. 构造期的版本比对与 `merge_dict` 升级

构造函数在配置读写之后，会**检查数据库里的配置版本是否落后于插件版本，落后就自动补齐新字段**。

### 2.1 全局配置部分（`:68-101`）

```python
configs: List[PluginConfiguration] = PluginConfiguration.select().where(
    PluginConfiguration.plugin_id == self.plugin_id            # :64-66
)

if self.__global_config_default is not None:                   # :68
    global_conf = next(
        (config for config in configs if config.channel_id == global_config_channel_key),   # :69-72
        None,
    )
    if global_conf is None:                                    # :73
        # 如果是插件初次安装初次加载，那么立刻应用global_default
        self.__set_global_config(self.__global_config_default)  # :75
        PluginConfigurationAudit.create(
            plugin_id=self.plugin_id,
            channel_id=global_config_channel_key,
            audit_time=datetime.now(),
            audit_reason='Plugin Initialize',                   # :80
            version=self.version,
        )
    else:                                                       # :83
        try:
            global_conf_json = json.loads(global_conf.json_config)   # :85
            # 比对版本
            if compare_version_numbers(global_conf.version, self.version) < 0:   # :87
                # 数据库的版本老，执行逐项更新
                merge_dict(global_conf_json, self.__global_config_default)       # :89
                self.__set_global_config(global_conf_json)                       # :90
                PluginConfigurationAudit.create(
                    ... audit_reason='Plugin Upgrade', version=self.version,     # :95-96
                )
        except json.JSONDecodeError:
            # 数据库中数据损坏，报错并用默认值覆盖
            log.error(f'数据库中插件{self.name}({self.plugin_id})的全局配置损坏，已重置为默认值。')   # :100
            self.__set_global_config(self.__global_config_default)                        # :101
```

三种情形：

| 情形 | 行号 | 行为 | 审计记录 |
| --- | --- | --- | --- |
| **全局配置记录不存在**（首次安装） | `:73-82` | 立刻写入 `global_config_default` | `Plugin Initialize`（`:80`） |
| **版本落后**（`compare < 0`） | `:87-97` | `merge_dict` 补全后写回 | `Plugin Upgrade`（`:95`） |
| **数据库 JSON 损坏** | `:98-101` | 捕获 `json.JSONDecodeError`，记 error，**用默认值覆盖** | 无审计记录 |

- **`compare_version_numbers(global_conf.version, self.version) < 0`（`:87`）**：参数顺序是「库里的版本, 插件版本」。`< 0` 表示库里更旧 → 需要升级。**相等或更新都不动**——所以插件降级（plugin version 变小）时**不会**回滚配置，用户的手动设置得以保留。
- **`merge_dict(global_conf_json, self.__global_config_default)`（`:89`）**：`merge_dict(target, source)` 的语义是**把 source 里 target 缺失的键补进 target**（实现 `core/util/common.py:269-284`）。这是「以用户已有配置为主，用默认值补齐缺失项」——**用户的自定义值不会丢**。
  - 细节：只补 `key not in target` 的（`core/util/common.py:272-274`）；类型不匹配时**用 source 覆盖**（`:276-277`）；dict 递归（`:279-280`）。
- ⚠️ **`json.JSONDecodeError` 的处理是破坏性的**：直接把用户配置重置为默认值（`:101`），**且不写审计记录**——这种重置在 `PluginConfigurationAudit` 里查不到，是排查「配置莫名回默认」的盲区。
- `configs` 只查询一次（`:64-66`），复用于全局与频道两段逻辑。

### 2.2 频道配置部分（`:103-122`）

```python
if self.__channel_config_default is not None:                  # :103
    for channel_conf in (config for config in configs if config.channel_id != global_config_channel_key):   # :104
        try:
            channel_conf_json = json.loads(channel_conf.json_config)      # :106
            if compare_version_numbers(channel_conf.version, self.version) < 0:   # :108
                merge_dict(channel_conf_json, self.__channel_config_default)      # :110
                self.__set_channel_config(channel_conf.channel_id, channel_conf_json)   # :111
                PluginConfigurationAudit.create(... audit_reason='Plugin Upgrade', ...)  # :112-118
        except json.JSONDecodeError:
            log.error(f'数据库中插件{self.name}({self.plugin_id})的频道配置损坏，已重置为默认值。')   # :121
            self.__set_channel_config(channel_conf.channel_id, self.__channel_config_default)   # :122
```

- **只遍历非全局记录**（`:104` 的生成器条件）。
- **只有插件提供了 `channel_config_default` 才做频道升级**（`:103`）——与 `get_config` 的 `:354` 分支呼应。
- 逐频道升级并逐条写审计（`:112-118`），所以一次升级可能产生**多条** `Plugin Upgrade` 记录（每条一个 `channel_id`）。
- 损坏处理与全局对称（`:119-122`）。

### 2.3 构造末尾调用 `deprecated_config_delete()`（`:124-126`）

`with log.sync_catch():`（`:125`）是**同步**异常捕获上下文（区别于 `log.catch` 的异步版），保证清理逻辑出错不会中断插件加载。**它每次构造插件实例时都会执行**（不是定时任务）——即**每次进程启动**都会检查一次。

> ⚠️ **为什么 `set_config` 会「跳过升级」**：`__set_channel_config` / `__set_global_config` 写入时会把 `version` 更新为当前插件版本（`:315`、`:319`、`:345`、`:349`）。此后 `compare_version_numbers(库里的版本, 插件版本)` 不再 `< 0`，`merge_dict` 补字段的路径就不会触发。控制台 `set_plugin_config` 同理（`core/server/plugin.py:137`、`:140`）。

## 3. 废弃配置项清理

### 3.1 `deprecated_config_delete()`（`:128-218`）

文档字符串（`:129-132`）：*「如果距离插件更新已经过去 n 天，移除既不存在于 default，也不存在于 Schema 的配置项。然后写入 Audit 信息。」*

```python
if self.__deprecated_config_delete_days is None or self.__deprecated_config_delete_days < 0:   # :133
    return
```

**`None` 或负数 = 关闭该功能**（`:133-134`）。默认是 `7`（`:39`）。

**第一步：找出每个 channel 最近一次的升级/废弃时间（`:136-149`）**

```python
max_audit_time_subquery = (
    PluginConfigurationAudit.select(
        PluginConfigurationAudit.channel_id,
        fn.MAX(PluginConfigurationAudit.id).alias('max_id'),      # :137-140
    )
    .where(
        (PluginConfigurationAudit.plugin_id == self.plugin_id)
        & (
            (PluginConfigurationAudit.audit_reason == 'Plugin Upgrade')
            | (PluginConfigurationAudit.audit_reason == 'Plugin Configuration Deprecated')   # :145
        )
    )
    .group_by(PluginConfigurationAudit.channel_id)                # :148
)
```

- 用 **`MAX(id)`**（自增主键）而不是 `MAX(audit_time)` 来取「最新」（`:139`）——自增 id 严格递增，不受时钟回拨/并发影响。
- **两种 reason 都算**：`Plugin Upgrade` 与 `Plugin Configuration Deprecated`（`:144-145`）。后者是关键——**一旦清理过，时间戳就刷新**，不会每次启动都重复清理。

**第二步：join 出最新记录（`:151-179`）**

```python
query = (
    PluginConfigurationAudit.select(
        PluginConfigurationAudit.channel_id,
        PluginConfigurationAudit.id,
        PluginConfigurationAudit.audit_time,
        PluginConfigurationAudit.audit_reason,
    )
    .join(
        max_audit_time_subquery,
        on=(
            (PluginConfigurationAudit.channel_id == max_audit_time_subquery.c.channel_id)
            & (PluginConfigurationAudit.id == max_audit_time_subquery.c.max_id)     # :161-162
        ),
    )
    .where(
        (PluginConfigurationAudit.plugin_id == self.plugin_id)
        & (PluginConfigurationAudit.audit_reason == 'Plugin Upgrade')               # :167
    )
)

result = [
    {'id': row.id, 'channel_id': row.channel_id, 'audit_time': row.audit_time, 'audit_reason': row.audit_reason}
    for row in query                                                                            # :171-179
]
```

- 子查询取「每个 channel 的最新 id」，再按 id 相等 join 回主表（`:158-164`）。
- **外层 where 又过滤成只要 `'Plugin Upgrade'`**（`:167`）——与子查询的「两种 reason 都取最新」形成配合：**子查询用两种 reason 定位「最近一次动过配置的时间点」，外层只挑出确实发生升级的那些行来执行清理**。
- 结果被**物化成 list**（`:171-179`）再处理——避免在迭代中做写操作干扰游标。

**第三步：超期则清理（`:181-218`）**

```python
for record in result:
    channel_id = record['channel_id']
    audit_time = record['audit_time']

    if audit_time < datetime.now() - timedelta(days=self.__deprecated_config_delete_days):   # :185
        if channel_id == global_config_channel_key:              # :188
            log.info('全局配置的配置项需要检查并剔除老旧配置项。')
            cfg = self.__get_global_config()                     # :191
            if cfg is not None:
                remove_uncommon_elements(
                    cfg, self.__global_config_default, self.__get_dynamic_global_config_schema()   # :193-195
                )
                self.__set_global_config(cfg)                    # :196
                PluginConfigurationAudit.create(
                    ... audit_reason='Plugin Configuration Deprecated', version=self.version,   # :201
                )
        else:                                                    # :204
            log.info(f'频道{channel_id}配置的配置项需要检查并剔除老旧配置项。')
            cfg = self.__get_channel_config(channel_id)          # :206
            if cfg is not None:
                remove_uncommon_elements(cfg, self.__channel_config_default, self.__get_dynamic_channel_config_schema())   # :208-210
                self.__set_channel_config(channel_id, cfg)       # :211
                PluginConfigurationAudit.create(... audit_reason='Plugin Configuration Deprecated', ...)   # :212-218
```

- **判定条件**（`:185`）：最后升级时间 + 7 天 < 现在。也就是**升级后满 7 天才清理**——给用户一个缓冲期去适应新配置项。
- 全局与频道两条路径完全对称（`:188-203` vs `:204-218`），只是取/存的函数与 schema 不同。
- 清理后写一条 `Plugin Configuration Deprecated` 审计（`:201`、`:216`），**这会让下次计算的「最新时间」前移，从而避免重复清理**。
- **全局记录的 `channel_id` 是 `''`**，所以 `:188` 的判断本质是「这条记录是不是全局的」。

### 3.2 `remove_uncommon_elements`（`:494-518`）

```python
def remove_uncommon_elements(source: dict, base: dict, schema: dict) -> None:
    """
    删除 source 中所有不在 base 中的元素
    """
    if base is None:                                    # :502-503
        return

    keys_to_remove = []
    for key in source:                                  # :507
        if key not in base:
            keys_to_remove.append(key)                  # :509

    if schema is not None:                              # :511
        if 'properties' in schema.keys():               # :512
            for key in schema['properties'].keys():     # :513
                if key in keys_to_remove:
                    keys_to_remove.remove(key)          # :515

    for key in keys_to_remove:                          # :517-518
        source.pop(key)
```

- **删除判定**：`source` 里有、`base`（即 default）里没有的键（`:507-509`）。
- **schema 提供豁免**（`:511-515`）：如果该键出现在 schema 的 `properties` 里，就**不删**。这保证「新版本刚加进 schema 但还没进 default」的字段不被误删。
- **`base is None` 时直接返回**（`:502-503`）——没有 default 就不做任何清理。
- **`source` 被原地修改**（`:518` 的 `source.pop`），返回值是 `None`。
- 只处理**顶层键**，不递归嵌套 dict（`:507` 的 `for key in source` 之后没有递归调用）。

## 5. 版本号比较

### 5.1 `compare_version_numbers`（`:470-491`）

```python
def compare_version_numbers(version1: str, version2: str) -> int:
    # 将版本号字符串分割成数字列表，忽略空值
    version1_numbers = [int(num) for num in version1.split('.') if num]     # :472
    version2_numbers = [int(num) for num in version2.split('.') if num]     # :473

    # 计算两个版本号列表的长度差
    length_difference = len(version1_numbers) - len(version2_numbers)       # :476

    # 如果一个版本号较短，将其扩展为与较长版本号相同的长度，用0填充
    if length_difference > 0:
        version2_numbers.extend([0] * length_difference)                    # :480
    elif length_difference < 0:
        version1_numbers.extend([0] * abs(length_difference))               # :482

    # 逐个比较版本号中的数字
    for num1, num2 in zip(version1_numbers, version2_numbers):              # :485
        if num1 > num2:
            return 1
        elif num1 < num2:
            return -1

    return 0                                                                # :491
```

- 返回 `1`（version1 更大）/ `-1`（更小）/ `0`（相等）。
- **补零对齐**（`:479-482`）让 `'1.0'` 与 `'1.0.0'` 判为相等——这与 `check_requirements` 的**字面量相等**（`core/plugins/__init__.py:83`）形成鲜明对比。
- **只支持纯数字段**：`int(num)` 遇到 `'v1'`、`'1.0-beta'` 会 **`ValueError`**（`:472-473`）。所以插件 `version` 必须是纯数字点号格式。
- `if num`（`:472`）过滤空段，所以 `'1..0'` 等价于 `'1.0'`。它是**模块级纯函数**（不是类方法），在 `:87`、`:108` 被直接调用。

### 5.2 两处版本比对语义不同

| 位置 | 语义 | `'1.0'` vs `'1.0.0'` |
| --- | --- | --- |
| `core/plugins/__init__.py:83`（依赖检查） | **字面量相等** | 不相等 → 报错 |
| `amiyaBotPluginInstance.py:470-491`（配置升级） | **数字比较 + 补零** | 相等 → 不升级 |

**不要混淆**。写 `Requirement` 时用精确版本号。

## 6. 辅助：`load()` 与 `LazyLoadPluginInstance`

### 6.1 `load()`（`:250-251`）

```python
def load(self):
    ...
```

- 基类是**空实现**（`...`），供子类覆写。
- 调用点：`core/plugins/__init__.py:58-60`，在所有插件安装完成后统一调用——所以 `load()` 里可以安全地访问其它插件。

### 6.2 `lazyLoadPluginInstance.py`：别名兼容（`:1-4`）

```python
from .amiyaBotPluginInstance import AmiyaBotPluginInstance

# 兼容性保留这个类变量
LazyLoadPluginInstance = AmiyaBotPluginInstance     # :4
```

- **`LazyLoadPluginInstance` 只是 `AmiyaBotPluginInstance` 的别名**，不是独立类、也不是子类（`:4` 是直接赋值）。
- 因此 `isinstance(x, LazyLoadPluginInstance)` 与 `isinstance(x, AmiyaBotPluginInstance)` **完全等价**。
- 导出链路：`core/plugins/customPluginInstance/__init__.py:2` → `core/__init__.py:23`，所以插件里可以 `from core import LazyLoadPluginInstance`。
- **V5 遗留**：老插件可能继承 `LazyLoadPluginInstance`，行为与继承 `AmiyaBotPluginInstance` 完全一致——**但「懒加载」这个语义在 V6 里已经不存在了**，名字有误导性。真正的「加载后钩子」是 `load()`（§6.1）。

### 6.3 `core/customPluginInstance.py` 转发模块

`core/customPluginInstance.py` 全文 1 行：`from core.plugins.customPluginInstance import *`。**它的存在意义是兼容旧版插件的 import 路径**：

- V6 重构把自定义插件实例从 `core/customPluginInstance.py` 挪到了 `core/plugins/customPluginInstance/` 包。
- 但 `plugins/*.zip` 里的插件是**独立发布的历史产物**，它们代码里写的是 `from core.customPluginInstance import AmiyaBotPluginInstance`（旧路径），不可能随宿主一起改。
- 保留这个转发模块，老插件的绝对导入路径就仍然有效。

**它为什么可用**：`core.customPluginInstance`（文件）与 `core.plugins.customPluginInstance`（包）是**不同层级上的同名物**，不构成遮蔽冲突。`core` 是普通包，其子模块 `core.customPluginInstance` 由文件 `core/customPluginInstance.py` 提供；该文件执行 `from core.plugins.customPluginInstance import *`，走的是完全独立的第二条路径。没有循环导入问题，因为 `core/plugins/customPluginInstance/__init__.py` 只导入同包内的三个子模块（`core/plugins/customPluginInstance/__init__.py:1-3`），不会反向导入 `core`。

**`core/frozen.py:7` 的 `import core.customPluginInstance`** 导入的正是这个转发模块（不是包）。它的作用与 `core/frozen.py` 里其它 import 一样——**让 PyInstaller 收集到这个转发模块及其背后的整条链路**（`amiyaBotPluginInstance` / `lazyLoadPluginInstance` / `requirement`）。见 [启动与单例 · 保活 import](01-启动与单例.md#22-一串保活-importcorefrozenpy3-15)。

> **实践建议**：新代码统一用 `from core.plugins.customPluginInstance import ...`（与 `core/__init__.py:23` 一致）。`core/customPluginInstance.py` 只作兼容保留，**不要往里加新内容**。
