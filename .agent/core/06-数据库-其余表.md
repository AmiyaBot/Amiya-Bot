### 1.3 `check_group_active`（`:35-37`）

```python
def check_group_active(group_id):
    group: GroupActive = GroupActive.get_or_none(group_id=group_id)
    return not (group and group.active == 0)
```

**插件的群开关判断全靠它**，语义是「默认激活」：

| 情形 | 计算 | 结果 |
| --- | --- | --- |
| 查不到记录 | `not (None and ...)` = `not None` | **`True`（激活）** |
| 记录存在且 `active == 1` | `not (group and False)` = `not False` | **`True`（激活）** |
| 记录存在且 `active == 0` | `not (group and True)` = `not True` | **`False`（休眠）** |

即**只有显式写入 `active=0` 才休眠**。这是「未配置即放行」的设计，避免新群因为没有记录而完全无响应。

### 3.1 `PluginConfiguration` — 插件配置（`:14-22`）

| 字段 | 行号 | 说明 |
| --- | --- | --- |
| `plugin_id` | `:16` | 插件 ID |
| `channel_id` | `:17` | **频道 ID，`''` 表示全局** |
| `json_config` | `:18` | **整份配置的 JSON 字符串**（`TextField`，非结构化） |
| `version` | `:19` | **写入时的插件版本**，升级比对的依据 |

**`primary_key = CompositeKey('plugin_id', 'channel_id')`（`:22`）是这张表的核心设计**：

- **复合主键**保证「一个插件的一个频道只有一条配置记录」——这是 `get_or_none(plugin_id=..., channel_id=...)`（`amiyaBotPluginInstance.py:294`、`:308`、`:323`、`:336`）能安全使用的前提。
- 因为已有复合主键，`plugin_id`（`:16`）与 `channel_id`（`:17`）**不需要再单独声明唯一性**。
- **`json_config` 存的是一整份 JSON 而不是逐项**——更新任一配置项都要「读出整份 → 改一个键 → 写回整份」（`amiyaBotPluginInstance.py:416-442`），**并发场景下存在丢失更新（last-write-wins）风险**。
- **`version` 字段是配置升级的锚点**，且在 `set_config` 时会被更新为当前版本（`amiyaBotPluginInstance.py:315`、`:319`、`:345`、`:349`）——这会让后续的 `merge_dict` 升级被跳过。

### 3.2 `PluginConfigurationAudit` — 配置审计（`:25-32`）

字段：`id`（`:27`，显式 `AutoField` 自增主键）、`plugin_id`（`:28`）、`channel_id`（`:29`，`null=True`）、`audit_time`（`:30`，`DateTimeField`，用 `datetime.now()` 写入）、`audit_reason`（`:31`）、`version`（`:32`）。

- **显式 `AutoField()` 自增主键**（`:27`），`deprecated_config_delete` 用 `fn.MAX(id)` 而非 `MAX(audit_time)` 取最新（`amiyaBotPluginInstance.py:136-149`）。
- **`audit_time` 是 `DateTimeField`**（不是时间戳），用 `datetime.now()` 写入。
- `audit_reason` 的三个取值：`'Plugin Initialize'`（`:80`）、`'Plugin Upgrade'`（`:95`、`:116`）、`'Plugin Configuration Deprecated'`（`:201`、`:216`）。
- **它只增不减**：没有清理机制。但每个插件/频道最多每次升级一条，量级可控。

> ⚠️ 数据库 JSON 损坏时配置会被**静默重置为默认值且不写审计**（`amiyaBotPluginInstance.py:98-101`、`:119-122`）——排查「配置莫名回默认」时这张表里查不到记录。

### 4.2 `UserInfo` — 用户状态（`:23-108`）

用户库里逻辑最重的模型。

| 字段 | 行号 | 默认 | 说明 |
| --- | --- | --- | --- |
| `user_id` | `:25` | — | **`ForeignKeyField(User, on_delete='CASCADE')`**，`db_column='user_id'` |
| `user_feeling` | `:26` | `0` | 好感度 |
| `user_mood` | `:27` | **`15`** | 心情值，**默认不是 0** |
| `sign_date` | `:28` | `NULL` | 签到日期（字符串） |
| `sign_times` | `:29` | `0` | 签到次数 |
| `jade_point` | `:30` | `0` | 当前理智/资源点 |
| `jade_point_max` | `:31` | `0` | 上限 |
| `meta_json` | `:32` | `'{}'` | **插件自由扩展的 JSON 容器** |

**`ForeignKeyField` 的关键点（`:25`）**：

- 外键指向 `User.user_id`，`on_delete='CASCADE'` 表示删 User 会级联删 UserInfo。
- **`db_column='user_id'`** 让物理列名就叫 `user_id`（否则 peewee 会默认加 `_id` 后缀）。
- **`user_id` 既是外键又是「看起来能直接比较的字段」**：代码里到处写 `UserInfo.user_id == user_id`（`:72`、`:108`、`core/server/user.py:37`），在 peewee 里比较的是外键的**原始值**，行为正确。

**`meta_json` 是插件扩展用户数据的官方途径**（`:32`）——避免每个插件都建自己的表。

#### `get_meta_value(user_id, key)`（`:34-48`）

```python
user: UserInfo = cls.get_user(user_id)          # :36
user_meta_json: str = user.meta_json             # :38
if user_meta_json is None or user_meta_json == '':   # :40-41
    user_meta_json = '{}'                        # :41
user_meta: dict = json.loads(user_meta_json)     # :43
if key in user_meta.keys():                      # :45
    return user_meta[key]
else:
    return {}                                    # :48
```

- **空值兜底**（`:40-41`）：NULL 或空串都当 `'{}'`。
- **缺失时返回 `{}` 而不是 `None`**（`:48`）——调用方可以直接 `value.get(...)` 或迭代，不会 `AttributeError`。但也意味着**无法区分「键不存在」和「值是空 dict」**。
- **`json.loads` 没有 try/except**（`:43`）：如果 `meta_json` 被写坏，这里会抛 `JSONDecodeError`。

#### `set_meta_value(user_id, key, data)`（`:50-72`）

```python
# 防止爆库，单个用户不可以超过1M数据，单项数据也限制为20K
try_dump = json.dumps(data)                      # :62
if len(try_dump) > 20 * 1024:                    # :63
    return None                                  # :64

user_meta[key] = data                            # :66
user_meta_json = json.dumps(user_meta)           # :67

if len(user_meta_json) > 1024 * 1024:            # :69
    return None                                  # :70

UserInfo.update(meta_json=user_meta_json).where(UserInfo.user_id == user.user_id).execute()   # :72
```

| 限额 | 行号 | 值 | 判定对象 |
| --- | --- | --- | --- |
| **单项** | `:63` | `20 * 1024` = **20 KB** | `json.dumps(data)` 的长度 |
| **单用户总量** | `:69` | `1024 * 1024` = **1 MB** | 合并后完整 JSON 的长度 |

- **注释 `:61` 明说动机**：「防止爆库」。
- ⚠️ **超限时返回 `None`，不抛异常也不报错**（`:64`、`:70`）——**静默丢弃**。插件写入失败时不会收到任何信号。排查「用户数据没存上」先算一下序列化长度。
- **两次检查的顺序**：先检查单项（`:62-64`，**写入前**），再检查总量（`:67-70`，**写入后但落库前**）。总量检查失败时 `user_meta` 在内存里已被污染，但**没有落库**，所以重读时会恢复。
- **用 `UserInfo.update(...)` 而非 `user.save()`**（`:72`）：直接发 UPDATE 语句，只更新一列，避免覆盖并发修改的其它字段。
- ⚠️ **长度按 `len(str)` 计算，即字符数不是字节数**（`:63`、`:69`）。中文 UTF-8 下实际字节数是 3 倍左右——**「20KB」实际可能是 60KB 字节**。

#### `get_user(user_id)`（`:74-77`）

```python
@classmethod
def get_user(cls, user_id):
    User.get_or_create(user_id=user_id)      # :76
    return cls.get_or_create(user_id=user_id)[0]   # :77
```

- **先确保 `User` 存在再建 `UserInfo`**（`:76-77`）——因为 `UserInfo.user_id` 是外键（`:25`），不先建 User 会违反外键约束。
- 第一行（`:76`）的返回值被丢弃，纯粹是为了「确保父记录存在」。
- **`get_or_create` 的并发风险**：两个协程同时为同一新用户调用会竞争插入，**可能抛唯一约束冲突**；本仓库未做防护。

#### `get_user_info(user_id)`（`:79-91`）

```python
user = convert_model(User.get_or_create(user_id=user_id)[0])              # :81
user_info = convert_model(cls.get_or_create(user_id=user_id)[0])          # :82
user_gacha_info = convert_model(UserGachaInfo.get_or_create(user_id=user_id)[0])   # :83
operator_box = convert_model(OperatorBox.get_or_create(user_id=user_id)[0])        # :84

return {
    'user': user, 'user_info': user_info,
    'user_gacha_info': user_gacha_info, 'operator_box': operator_box,
}                                                                          # :86-91
```

- **一次性把 4 张表的记录都 `get_or_create` 出来**，用 `convert_model` 转成普通字典返回——「聚合查询」，避免 N 次往返。
- **副作用**：因为用 `get_or_create`，**即使只是想读数据，也会插入 4 条新记录**。
- **注意 `:82` 用的是 `cls.get_or_create` 而不是 `cls.get_user`**——它**跳过了 `:76` 的「先建 User」步骤**。这在 `:81` 已经建过 User 之后是安全的（`:81` 先执行），**顺序不能调换**。

#### `add_jade_point(user_id, point, point_max)`（`:93-108`）

```python
user: UserInfo = cls.get_user(user_id)      # :95

surplus = point_max - user.jade_point_max   # :97
if surplus <= 0:                            # :98
    return None                             # :99

if point > surplus:                         # :101
    point = surplus                         # :102

update = {
    'jade_point': UserInfo.jade_point + point,          # :105
    'jade_point_max': UserInfo.jade_point_max + point,  # :106
}
cls.update(**update).where(UserInfo.user_id == user_id).execute()   # :108
```

- **语义**：增加资源点，但**受 `point_max` 上限约束**。
- **`:97` 的 `surplus` 计算方式很关键**：`point_max - user.jade_point_max`——**用「新的上限」减「当前上限」**，而不是「上限 - 当前值」。所以 **`point_max` 参数是「此次要抬升到的上限」**，`surplus` 是「上限抬升了多少」。误传成「上限值」会算出错误的 surplus。
- **`:98-99`**：上限没提升就不加（返回 `None`）。
- **`:101-102`**：单次增加不超过上限增量。
- **`:104-107` 用 `UserInfo.jade_point + point`（字段对象 + 字面量）构造原子自增 SQL**——peewee 的 F 表达式用法，**在数据库侧做加法，避免了读改写竞态**。这是本仓库里少有的并发安全写法。
- **`jade_point` 与 `jade_point_max` 同步增长**（`:105-106`），所以扣除 `jade_point` 时不减 `_max`——即「上限只涨不跌」。

### 4.4 `OperatorBox` — 抽卡图鉴（`:122-125`）

```python
@table
class OperatorBox(UserBaseModel):
    user_id: str = CharField()                        # :124
    operator: str = TextField(default='')             # :125
```

- ⚠️ **`user_id` 是普通 `CharField`，不是外键**（`:124`），而 `UserInfo`（`:25`）与 `UserGachaInfo`（`:113`）都是。所以**删 User 不会级联删 OperatorBox**——会留下孤儿数据。这是三张用户子表之间的**唯一例外**。
- **`operator` 字段是手写序列化格式**（`pluginsDev/src/arknights/gacha/gachaBuilder.py:573-592`）：
  ```python
  box_res = '|'.join([':'.join([str(i) for i in item]) for n, item in box_map.items()])   # :590
  ```
  即 **`名字:稀有度:数量` 用 `|` 拼接**，例如 `能天使:6:2|德克萨斯:5:1`。
  - 读取解析（`gachaBuilder.py:577-580`）：
    ```python
    for n in user_box.operator.split('|'):
        n = n.split(':')
        box_map[n[0]] = [n[0], int(n[1]), int(n[2])]
    ```
  - `box.py:21-22` 同样用 `item.split('|')` + `split(':')` 三元组解包。
  - **这个字段不可随意改动**——读写两端 + `box.py` 三处都必须同步。
  - **空串是合法的初始值**（`:125` 的 `default=''`），读取时用 `if not box or not box.operator` 兜底（`box.py:13`）。
- **写入方式是整体覆盖**：`OperatorBox.update(operator=box_res).where(...)`（`gachaBuilder.py:592`），不是增量更新。所以并发抽卡有丢失风险。
- **只在官方卡池时记录**（`gachaBuilder.py:508-509`）：`if self.pool.is_official: self.set_box(operators)`——自定义卡池不写入 box。

### 4.5 用户库小结

| 表 | 与 `User` 的主键关系 | 备注 |
| --- | --- | --- |
| `User` | — | 主表 |
| `UserInfo` | 外键 + CASCADE | 含 `meta_json` 扩展容器（20KB/项、1MB/用户） |
| `UserGachaInfo` | 外键 + CASCADE | 抽卡状态 |
| `OperatorBox` | **普通字段，无外键** | ⚠️ 删用户不级联；手写序列化格式 |
