## 4. `threadPool.py`

```python
executor = ThreadPoolExecutor(min(32, (os.cpu_count() or 1) + 4))   # core/util/threadPool.py:7

async def run_in_thread_pool(block_func, *args, **kwargs):          # :10-12
    loop = asyncio.get_event_loop()
    return await loop.run_in_executor(executor, partial(block_func, *args, **kwargs))
```

- `:7` **进程级全局单例**线程池，容量 `min(32, cpu+4)`。`(os.cpu_count() or 1)` 防御 `cpu_count()` 返回 `None`。
- `:11` `partial` 把参数绑成无参可调用对象，因为 `run_in_executor` 不接受 kwargs。
- `:12` 返回异步结果，调用方 `await` 即可把阻塞函数变成 awaitable。

**为什么需要**：本项目是 asyncio 事件循环驱动，但需调用的第三方 SDK 都是**同步阻塞**的：

| 被包装的阻塞操作 | 位置 |
| --- | --- |
| 百度云 NLP/OCR/内容审核 SDK | `core/lib/baiduCloud.py:33,47,59,77,88` |
| `requests-html` 的 `HTMLSession().get` | `pluginsDev/src/arknights/arknightsGameData/builder/wiki.py:100`、`pluginsDev/src/replace/main.py:35` |
| PaddleOCR 推理（CPU 密集，秒级） | `pluginsDev/src/arknights/recruit/main.py:263,279` |
| 第三方 LLM HTTP SDK | `pluginsDev/src/ai/blm/src/*/*_adapter.py`（如 `deepseek/deekseek_adapter.py:11`） |
| 网络图片上传（COS） | `core/cosChainBuilder.py:45` |

直接在协程里调用这些同步函数会**阻塞整个事件循环**，所有 QQ 消息处理一起卡住。

**坑**：

- 线程池**全局共享**，所有插件共用这 ≤32 个线程。某插件发起大量并发 OCR/LLM 会耗尽线程，导致其它插件的调用排队等待。
- 默认 `ThreadPoolExecutor` 的 `max_workers` 是硬上限，任务多时**只排队不扩容**。
- 线程内的代码运行在**非主线程**，绑定的函数**只能是同步函数**（函数体内不能 `await`）。
- 该模块被插件**按路径直接导入**（`pluginsDev/src/ai/blm/src/deepseek/deekseek_adapter.py:11`
  写 `from core.util.threadPool import run_in_thread_pool`），故文件名/函数名属兼容性契约。

## 5. `timeRecorder.py`

```python
class TimeRecorder:
    def __init__(self):                 # core/util/timeRecorder.py:6-7
        self.time = time.time()

    def rec(self, millisecond=False):   # :9-11
        mil = 1000 if millisecond else 1
        return int(time.time() * mil - self.time * mil)

    def total(self):                    # :13-14
        return self.calc_time_total(self.rec())

    @staticmethod
    def calc_time_total(seconds):       # :16-31
        ...
```

- `:6-7` 构造时用 `time.time()`（**墙上时钟**，非 monotonic）打时间戳。
- `:9-11` `rec()` 返回自构造以来的经过时间，默认**秒**（int），`millisecond=True` 时返回**毫秒**。
- `:13-14` `total()` = 把 `rec()` 的秒数交给 `calc_time_total` 转成中文可读串。
- `:16-31` `@staticmethod`，**可不经实例直接调用**。用 `datetime.timedelta` 拆天/时/分/秒，只拼接非零单位；
  全为 0（耗时不足 1 秒）时返回**空字符串**。

调用方：静态调用 `TimeRecorder.calc_time_total(seconds)` → `pluginsDev/src/admin/main.py:43,71`；
实例 + `.total()` → `pluginsDev/src/game/guess/main.py:85,154`、`pluginsDev/src/arknights/arknightsGameData/main.py:31,35,45,49,57,61`、
`pluginsDev/src/weibo/main.py:307,367`。

**坑**：空串返回会让调用方拼出「耗时」这样的残缺文案；用 `time.time()` 而非 `monotonic()`，
系统时钟被 NTP 校正/手动调整时结果可能为负或跳变。

## 6. `zipTools.py`

```python
def extract_zip_plugin(curr_dir, resource_path):     # core/util/zipTools.py:8-16
    create_dir(resource_path)
    pack = zipfile.ZipFile(curr_dir)
    for pack_file in support_gbk(pack).namelist():
        if pack_file.endswith('.py'):
            continue
        if os.path.exists(os.path.join(resource_path, pack_file)):
            continue
        pack.extract(pack_file, resource_path)


def support_gbk(zip_file: zipfile.ZipFile):          # :19-27
    name_to_info = zip_file.NameToInfo
    for name, info in name_to_info.copy().items():
        real_name = name.encode('cp437').decode('gbk')
        if real_name != name:
            info.filename = real_name
            del name_to_info[name]
            name_to_info[real_name] = info
    return zip_file
```

### `extract_zip_plugin`（`:8-16`）

- `:9` `create_dir(resource_path)` 确保目标目录存在。
- `:12-13` **跳过所有 `.py`**：插件包的 Python 代码由框架插件加载流程处理，不走资源解压。
- `:14-15` **已存在的文件不覆盖**：增量解压，保留用户/历史文件。
- **无仓内调用方**（全仓检索仅 `:8` 定义处 + `.pyc`），属遗留/插件 API。
- `zipfile.ZipFile(curr_dir)` 未加 `with`，异常时文件句柄不关闭。

### `support_gbk`（`:19-27`）

- `:20` `zip_file.NameToInfo` 是 `{文件名: ZipInfo}` 映射。
- `:22` 核心一行 `name.encode('cp437').decode('gbk')`：Windows 自带「压缩到 zip」在文件名非 ASCII 时
  用 GBK 字节写出，但 **zip 规范标记的是 cp437**，于是 Python 的 `zipfile` 按 cp437 解码得到乱码。
  这里反向编码回原始字节再用 GBK 解码，还原中文名。
- `:23-26` 名字确实变了才替换：改 `info.filename`、从 `NameToInfo` 删旧键、建新键。
  用 `.copy()`（`:21`）迭代是为了**边遍历边改字典**不报错。
- `:27` 返回同一个 `ZipFile` 对象，故可链式 `support_gbk(pack).namelist()`。

**为什么需要**：社区插件由作者用 Windows 压缩工具打包上传，中文文件名（如「立绘」「材料」目录）
在 Linux/Docker（bot 运行环境）下不修复就会解压出乱码路径，后续按名字读取资源必然失败。

调用方：`support_gbk` → `core/resource/botResource.py:6,39`（解压 `Amiya-Bot-assets.zip`，见 [03-外部服务.md](03-外部服务.md)）。

**坑**：

- `:22` 对**已经是 UTF-8 文件名**的条目也会尝试 `encode('cp437')`。含中文的 UTF-8 名在 cp437 下不可编码会抛出
  `UnicodeEncodeError`，且 `:22` 没有 try/except——**混用编码的 zip 会导致整个解压流程崩溃**。
- 该函数**原地修改**传入的 ZipFile，不是纯函数。
- `:23` 用「结果不同才替换」做判断是启发式：纯 ASCII 名在两种编码下相同故不会被误改，
  这也是它能安全处理混合包的原因。
