# 外部服务

三块对外依赖封装：百度云 AI（`core/lib/baiduCloud.py`）、Git 自动化（`core/lib/gitAutomation.py`）、
资源包下载（`core/resource/botResource.py`）。

三者都涉及网络/进程阻塞，前两者的 SDK 调用经 [02-工具函数.md](02-工具函数.md) 的 `run_in_thread_pool` 下放到线程池。

---

## 1. `core/lib/baiduCloud.py`

对百度 AI SDK（`aip` 包：`AipNlp` / `AipOcr` / `AipContentCensor`）的异步薄封装，共 91 行。

### enable 开关

`core/lib/baiduCloud.py:9-22`：

```python
def __init__(self, conf):
    self.enable = False
    self.__nlp = None; self.__ocr = None; self.__cc = None
    if conf.enable:
        options = (str(conf.appId), conf.apiKey, conf.secretKey)
        self.__nlp = AipNlp(*options)
        self.__ocr = AipOcr(*options)
        self.__cc  = AipContentCensor(*options)
        self.enable = True
```

- `:15` 由配置项 `conf.enable` 决定是否初始化三个 SDK 客户端；未开启时三者保持 `None`、`enable=False`。
- `:16` `str(conf.appId)` —— 显式转字符串（YAML 里若写成数字会被解析成 int，SDK 需要 str）。
- **每个方法开头都先判 `if not self.enable: return False`**（`:28-29,42-43,54-55,70-71,84-85`），
  即关闭状态下所有调用点**统一拿到 `False`** 而不抛异常。

### 五个方法

全部经 `run_in_thread_pool` 走线程池，并用 `async with log.catch()` 兜异常（异常被记录并吞掉）：

| 方法 | 行号 | 百度接口 | options | 返回语义 |
| --- | --- | --- | --- | --- |
| `emotion(text)` | `:24-36` | `AipNlp.emotion`（对话情绪识别） | `{'scene': 'talk'}` | 含 `error_code` → `False`，否则原始 dict |
| `web_image_url(url)` | `:38-48` | `AipOcr.webImageUrl`（网络图片文字识别） | `{'detect_direction': 'true'}` | 直接返回 dict，**不检查 `error_code`** |
| `basic_general(image)` | `:50-64` | `AipOcr.basicGeneralUrl`（str）或 `AipOcr.basicGeneral`（bytes） | `{'detect_direction': 'true'}` | 按 `type(image) is str` **运行时分派**两个 SDK 方法（`:60`） |
| `basic_accurate(image)` | `:66-78` | `AipOcr.basicAccurate`（高精度） | `{'detect_direction': 'true'}` | URL 先 `download_async` 拿流再传；`stream` 为空时**隐式返回 `None`** |
| `text_censor(text)` | `:80-90` | `AipContentCensor.textCensorUserDefined`（文本审核） | 无（只传 text） | 含 `error_code` → `False`，否则原始 dict |

- `:60` 的分派差异：`basic_general` 接受 URL 字符串（走 `basicGeneralUrl`），
  而 `basic_accurate` 不区分——URL 会先下载成字节流再走本地图片接口（`:74`）。
- `:31,45,57,73,87` 的 `log.catch()` 意味着调用方拿到的可能是 `False` / `None` 而不是异常。
- `from core import log`（`:5`）即 amiyabot 的 logger。

### 配置文件

- 仓库内模板：`resource/plugins/baiduCloud.yaml`，4 个键 `enable: false` / `appId:` / `apiKey:` / `secretKey:`（空值）。
- 每个使用方插件**自带同名副本并在启动时拷到 `resource/plugins/`**：
  `pluginsDev/src/user/baiduCloud.yaml`、`pluginsDev/src/arknights/recruit/baiduCloud.yaml`、`pluginsDev/src/replace/baiduCloud.yaml`。
  拷贝逻辑见 `pluginsDev/src/user/main.py:14,18`、`pluginsDev/src/arknights/recruit/main.py:30,35`、
  `pluginsDev/src/replace/main.py:17,21`（均为 `config_path = 'resource/plugins/baiduCloud.yaml'` + `shutil.copy`）。
- 构造方式有两种：`BaiduCloud(read_yaml(config_path))`（`pluginsDev/src/user/main.py:20`、`pluginsDev/src/replace/main.py:23`）
  与 `BaiduCloud(attridict(conf))`（插件内配置项，`pluginsDev/src/arknights/recruit/main.py:186`）。

### 调用方

| 调用 | 位置 |
| --- | --- |
| `await baidu.text_censor(nickname)` | `pluginsDev/src/user/main.py:66` |
| `await baidu.basic_accurate(data.image[0])` / 失败后 `await baidu.basic_general(...)` | `pluginsDev/src/arknights/recruit/main.py:244,246` |
| `await baidu.text_censor(replace)` | `pluginsDev/src/replace/main.py:179` |

`emotion` / `web_image_url` 无仓内调用方，属公共 API。

`core/frozen.py:11` 有 `from core.lib import baiduCloud` —— 该文件是 PyInstaller 冻结环境的「确保子模块被收集」清单
（配合 [../deploy/02-打包发行.md](../deploy/02-打包发行.md) 的 `--hidden-import`），
说明 `baiduCloud` 是动态使用、静态分析扫不到的模块。

### 坑

- `web_image_url` / `basic_general` / `basic_accurate` **不检查 `error_code`**，只返回 SDK 原始 dict；
  只有 `emotion` / `text_censor` 做检查。调用方必须自己判断返回值形状（`bool` 还是 `dict`）——这是返回类型注解为
  `Union[bool, dict]` 的原因。
- `basic_accurate` 在 `stream` 为空时**落到函数末尾返回 `None`**（`:74-78` 整块在 `if` 内），
  `None` / `False` / `{}` 的区分在调用方容易出错。
- `enable=False` 返回 `False`，而 `text_censor` 的 `False` **既可表示「审核未通过」也可表示「功能未开启」**
  ——`pluginsDev/src/user/main.py:66` 一类调用点无法区分这两种情况。
- 配置经 `read_yaml` 得到 `attridict` 对象，故 `conf.appId` 是属性访问；
  `recruit/main.py:186` 传插件 config 时，字段名必须是 `enable`/`appId`/`apiKey`/`secretKey` 四个 camelCase 键。

## 2. `core/lib/gitAutomation.py`

对 `GitPython`（`git` 包）的封装，用于在插件里**自动克隆/更新游戏数据仓库**（60 行）。

### `Progress` 进度类

```python
class Progress(git.RemoteProgress):                  # core/lib/gitAutomation.py:10-12
    def update(self, *args, **kwargs):
        GitAutomation.progress(*args, **kwargs)
```

`:10-12` 重写 `git.RemoteProgress.update`，把每次进度回调**转发**给 `GitAutomation.progress` 静态方法。

`GitAutomation.progress`（`:21-38`，`@staticmethod`）：

- `:28-30` 把 `cur_count/max_count` 换算成百分比，再按 4% 一格生成 25 格的 `=` 进度条。
- `:32-33` `\r` 回到行首 + 打印 `Fetching [====     ] cur / max (n%) message`，`end=''` 实现原地刷新。
- `:35` `sys.stdout.flush()` 保证即时输出。
- `:37-38` `cur_count >= max_count` 时补一个换行，结束进度条行。

### `update(options)`（`:40-60`）

1. `:41` 记日志 `Pulling repo "{url}" -> "{dir}"...`。
2. `:42-48` **目标目录不存在 → 克隆**：`git.Repo.clone_from(url, to_path=..., progress=self.progress, multi_options=options or [])`。
3. `:49-52` **目录已存在 → 拉取**：`git.Repo(dir)` 后 `repo.remotes.origin.pull(progress=self.progress)`。
   **注意**两条路径都是直接传 `self.progress`（静态方法），不会走到 `Progress` 类。
4. `:53-55` `git.InvalidGitRepositoryError`（目录存在但不是 git 仓库）→ `shutil.rmtree(self.repo_dir)` **删掉整个目录后递归重试** `self.update(options)`。
5. `:56-58` `git.GitCommandError` → `log.error(e)` + `log.warning('Git 操作失败，请确保 "git" 命令能够正确执行或删除目录 "..." 后重试')`，**不重试、不抛出**。
6. `:59-60` 兜底 `except Exception` → 仅 `log.error(e)`。

### 调用方

`pluginsDev/src/arknights/arknightsGameData/builder/__init__.py:64`：
`GitAutomation(gamedata_path, repo).update(['--depth 1'])` —— 用浅克隆拉游戏数据仓库。
`GitAutomation` 由 `core/__init__.py:20` 再导出，插件从 `core` 直接 import
（`builder/__init__.py:12` 的 `from core import AmiyaBotPluginInstance, GitAutomation, log`）。

### 坑

- `:53-55` 的「删目录重试」是**破坏性操作**：任何让 `git.Repo(dir)` 抛 `InvalidGitRepositoryError` 的情况
  （用户手工放了别的东西、`.git` 被删、磁盘损坏）都会**静默删除用户目录**，若该目录内有用户数据会不可逆丢失。
- `:56-58` 捕获 `GitCommandError` 后**不抛出**，调用方 `builder/__init__.py:64` 无法感知失败，
  后续读取数据会遇到「目录为空/不存在」的间接错误，而非明确的 git 错误。
- **依赖外部 `git` 可执行文件**（`log.warning` 文案明确提示），Docker 镜像必须装有 git（见 [../deploy/01-入口与Docker.md](../deploy/01-入口与Docker.md)）。
- `self.branch`（`:16,19`）被保存但 `update` 中**从未使用**，实际拉取的是仓库默认分支，而非构造时传入的 `branch`。
- `progress` 用 `print` 而非 logger，容器/重定向 stdout 的环境下进度条会污染日志文件。

## 3. `core/resource/botResource.py`

`core/resource/__init__.py:1` 只有一行 `from core.config import remote_config`，
把 `remote_config` 借 `core.resource` 命名空间再导出给插件用（见 [01-配置.md](01-配置.md)）。

### 完整流程

`BotResource.download_bot_resource()`（`core/resource/botResource.py:11-50`，`@classmethod`）：

```python
create_dir('resource')                                            # :13
url        = f'{remote_config.remote.cos}/resource/assets/Amiya-Bot-assets.zip'   # :15
version    = f'{remote_config.remote.cos}/resource/assets/version.txt'            # :16
lock_file  = 'resource/assets-lock.txt'                           # :17
pack_zip   = 'resource/Amiya-Bot-assets.zip'                      # :18
```

1. `:13` 确保 `resource/` 存在（相对 CWD，必须在仓库根启动）。
2. `:23` `latest_ver = download_sync(version, stringify=True)` —— **同步**下载版本号文本。
3. **版本比对**（`:24-30`）：
   - 锁文件存在且 `latest_ver` 有值时，读锁文件内容与 `latest_ver` 比较，**不等则 `flag = True`**（`:24-28`）。
   - **锁文件不存在 → 直接 `flag = True`**（`:29-30`），强制走一次下载。
   - **若 `latest_ver` 为 `None`（版本请求失败）而锁文件存在，`flag` 保持 `False`，本次跳过更新。**
4. **下载与解压**（`:32-44`）：
   - `:33` `download_sync(url, progress=True)` 带进度条下载整包（**全量下载**，无断点续传/增量）。
   - `:34-36` 成功则写 `resource/Amiya-Bot-assets.zip`。
   - `:38-40` `zipfile.ZipFile(pack_zip)` 后 `support_gbk(pack).namelist()` 逐项 `pack.extract(pack_file, 'resource')`
     —— 用 [02-工具函数.md](02-工具函数.md) 的中文文件名修复，**解压到 `resource/` 根**（zip 内路径决定实际落点）。
     与 `extract_zip_plugin` 不同，这里**没有**「跳过 .py」「已存在则不覆盖」的逻辑。
   - `:41-44` 下载失败（`data` 为空）时：**若锁文件存在则先删除它**，然后 `raise Exception('assets download failed')`。
5. **写锁**（`:46-48`）：`latest_ver` 有值则把版本号写入 `resource/assets-lock.txt`；
   `:49-50` 否则 `log.error('assets version file request failed.')`。

### 「失败时删锁重试」的语义

锁文件记录的是**已成功落盘的资源版本**。若下载失败却保留锁，下次启动时「锁内容 == 远端 version」
会判定为最新，**永远不再尝试下载**，资源将永久停留在旧版本/半成品状态。
所以失败分支主动删锁（`:42-43`）= 强制「下次启动重新尝试」。

**推论**：删掉 `resource/assets-lock.txt` 是手动强制刷新资源的官方手段。

### `support_gbk` 的作用

资源包内含中文命名的立绘/材料/素材目录，Linux/Docker 下若不修复 cp437→gbk 乱码，
解压出的中文路径将无法被后续代码按名访问（详见 [02-工具函数.md](02-工具函数.md) §6）。

### 同步阻塞

`amiya.py:21` 在 `run_amiya` 的 `try` 块里**直接调用** `BotResource.download_bot_resource()`，
调用点在 `asyncio.run(main())`（`amiya.py:29`）**之前**，即**没有任何协程/线程包装、纯同步阻塞**
（见 [../deploy/01-入口与Docker.md](../deploy/01-入口与Docker.md)）。

后果：

- 启动阶段（事件循环尚未开始）串行执行：先一次版本请求，可能再下载整个资源包 + 解压。
- 资源包体积大或网络慢时，**bot 在完成前完全无响应**，日志停在 `checking assets update...`（`botResource.py:20`）。
- 首次部署/换版本/删锁后的启动会明显变慢，是排查「启动卡住」时首先要看的地方。
- 也是 Docker 健康检查/`entrypoint.sh` 超时的常见诱因。

### 坑

- `download_sync(...)` 未传超时参数，网络挂起时会一直等。
- `:38` 未加 `with`，`ZipFile` 句柄依赖 GC 关闭；`:26,35,47` 的 `open` 同样用裸 `open`。
- 下载的 zip **不删除**（`resource/Amiya-Bot-assets.zip` 常驻磁盘），只作为解压中间产物。
- `raise Exception(...)`（`:44`）在 `asyncio.run` 之前抛出，被 `amiya.py:30-31` 的 `except KeyboardInterrupt` **漏掉**
  ——资源下载失败会直接以未捕获异常终止进程（非零退出码），是「容器反复重启」的一个可能原因。
